---
topic: DI Migration to Pure FactoryKit Registrations
updated: 2026-09-24T21:57
---

- (decision) Spec purpose: migrate iOS dependency injection from manual assembly structs to pure FactoryKit declarative registrations across the entire dependency graph
- (decision) Why: Current DI uses manual DataSourcesAssembly/RepositoriesAssembly structs called from Factory closures — creates maintenance burden, obscures dependency graph, prevents FactoryKit scope optimization, and complicates test assembly configuration
- (capability) CAP-1: Migrate all DataSource dependencies (APIClient, SessionController, SessionRefreshing, InstalledDatasetRegistry) to Factory registrations with intentional scopes (singleton for SessionController, cached for APIClient)
- (capability) CAP-2: Migrate all Repository implementations to Factory registrations, preserving DEBUG/UITest conditional override for AuthRepository and keeping UnavailableXRepository placeholders for unimplemented domains
- (capability) CAP-3: Remove all manual assembly structs (DataSourcesAssembly.swift, RepositoriesAssembly.swift, AppInfrastructure.swift) from DependencyInjection folder
- (capability) CAP-4: Simplify ProductionAssembly.makeContainer() to only register config overrides (baseURL, transport) and refactor TestAssembly.makeGraph() to use Container.shared + FactoryTesting scopes exclusively
- (capability) CAP-5: All unit and UI tests pass with new structure (make -C apps/ios check succeeds) and no regression in Debug/Release builds
- (constraint) iOS architectural rules are mandatory: Domain free of UI/infrastructure dependencies; Data maps wire DTOs to Domain; Presentation accesses data only through Domain use cases
- (constraint) Dependencies assembled manually under App/DependencyInjection/; pass UseCases to UI code, not repositories, API clients, or dependency containers
- (constraint) Preserve Step-Driven Coordinator flow: Views do not invoke coordinators directly
- (constraint) FactoryKit already integrated via SPM; must use Factory scopes (singleton, cached, new) intentionally per dependency type
- (constraint) Tests must use Container.shared + FactoryTesting only; no custom test assemblies with manual wiring
- (decision) Non-goal: Migrate to a different DI framework (FactoryKit is already adopted and stays)
- (decision) Non-goal: Change public API contracts of repositories, use cases, or data sources — migration is internal wiring only
- (decision) Non-goal: Introduce property-wrapper based injection (@Injected) — FactoryKit closure-based registration pattern is the standard
- (decision) Success signal: make -C apps/ios check passes (lint + unit tests + UI tests) and DependencyInjection folder contains only AppContainer.swift, Container+Registrations.swift, UseCases.swift, ProductionAssembly.swift, UITestAuthRepository.swift
- (assumption) FactoryKit's default 'cached' scope is safe starting point for most dependencies; can promote to singleton where needed
- (assumption) DEBUG/UITest conditional for AuthRepository can be expressed cleanly within Factory registration using #if DEBUG || UITEST
- (question) Open question: What is the correct Factory scope for each repository (singleton vs cached vs new)? Input only specifies SessionController=singleton, APIClient=cached; remaining repositories undefined
- (question) Open question: Should httpTransport, apiBaseURL, tokenStore remain as singleton Factory registrations or are there cases where cached/new is more appropriate?
- (question) Open question: How to handle UnavailableXRepository placeholders — keep as Factory registrations returning unavailable implementations, or remove entirely until domains are implemented?
- (question) Open question: Does AppInfrastructure.swift have any remaining references outside DependencyInjection/ that would prevent deletion?
- (question) Open question: Are there any circular dependency risks in the current graph that FactoryKit would detect at runtime? Current registrations file is 167 lines — review needed before merge
- (decision) CAP-1 success: All DataSource types (APIClient, SessionController, SessionRefreshing, InstalledDatasetRegistry) registered in Container+Registrations with correct scopes; no manual DataSourcesAssembly references remain
- (decision) CAP-2 success: All Repository implementations registered in Container+Registrations; DEBUG/UITest AuthRepository override works; UnavailableXRepository placeholders present for unimplemented domains
- (decision) CAP-3 success: DataSourcesAssembly.swift, RepositoriesAssembly.swift, AppInfrastructure.swift deleted; no imports of these files remain anywhere in the codebase
- (decision) CAP-4 success: ProductionAssembly.makeContainer() only overrides config values; TestAssembly.makeGraph() uses Container.shared + FactoryTesting scopes; no manual assembly in test setup
