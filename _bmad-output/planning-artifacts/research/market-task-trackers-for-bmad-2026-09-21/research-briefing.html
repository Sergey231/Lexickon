Решение: начать с GitHub Projects

verified synthesis BMAD хранит PRD, архитектуру, эпики, истории и состояние спринта в Markdown/YAML рядом с кодом. GitHub Issues и Projects добавляют представление для людей без отдельного контура интеграции: задачи, pull-реквесты, Actions, CLI и API находятся в одной системе [1] [2] [3] [4] [5].

GitHub Projects · 4,49

Лучший баланс нативности, автоматизации и цены.

Linear · 4,42

Лучше для product/UX-команды и явной продуктовой иерархии.

YouTrack · 4,33

Лучшее соотношение цены и возможностей; сильный Markdown/self-hosted сценарий.

Оговорка: источником истины остаются BMAD-файлы в Git. Трекер хранит идентификатор, краткое описание, статус, связи и ссылку на файл.

Двухнедельный пилот

  1. Сначала подтвердить, что внешний трекер вообще нужен участникам проекта.
  2. Сохранить `sprint-status.yaml` и story files источником истины.
  3. Представить Epic/Story/Task типами issues либо метками и шаблонами; связи — sub-issues.
  4. В истории хранить ссылку на `.md`, не полную копию.
  5. Связать PR с историей; после merge менять статус через Actions/Projects workflow.
  6. Начать с односторонней синхронизации Git/BMAD → Project.
  7. Экспортировать TSV и проверить восстановление иерархии через GraphQL.

Успех: ≤1 ручного обновления на историю; нет конфликтов с YAML; доска понятна без чтения репозитория; участники вне разработки ей пользуются; связи восстанавливаются из экспорта/API.

Перейти на Linear, если product/UX участники избегают GitHub Projects или регулярно нарушают принятую модель. Это условие важнее разницы 0,07 балла.

Что нужно BMAD

verified Официальный поток идёт от анализа и PRD через UX/архитектуру к эпикам и историям, затем создаёт `sprint-status.yaml`; реализация выполняется по одной истории [1]. Устойчивое ядро иерархии — эпик → история; отдельная сущность Task полезна, но не обязательна [2].

  • Markdown/YAML в Git — источник истины.
  • Эпики, истории и необязательные задачи отображаются в трекере.
  • Статусы автоматизируются через API, CLI, вебхуки или Actions.
  • PR и коммиты связываются с историями.
  • Данные выгружаются в открытом формате или полностью через API.

Почему GitHub Projects победил

primary vendor evidence Issues поддерживает многоуровневые sub-issues; Projects добавляет board/table/roadmap, поля и автоматизации [3] [4]. GraphQL, `gh api` и Actions программно меняют данные Projects [5]. TSV-экспорт подтверждён [6]. Страница цен перечисляет Issues & Projects в Free, GitHub Team — $4/пользователь/месяц [7].

BMAD story file → GitHub Issue → Pull Request → Project status

Синхронизация со статусами PR/checks — вывод из доступных API и Actions, который следует подтвердить пилотом. Главный риск — отсутствие готовой BMAD-семантики: типы, шаблоны, статусы и правила иерархии придётся поддерживать дисциплиной команды.

Когда выбрать другой трекер

Linear

primary evidence Для активной product/UX-команды: явная иерархия [8], GitHub-интеграция [9], Markdown/CSV/API export [10]. Basic $10, Business $16 при годовой оплате [11].

YouTrack

primary evidence Для CommonMark, JS-workflows и Cloud → Server [12] [13] [15]. GitHub/VCS интеграция [14]. Бесплатно до 10 пользователей; далее от $5,40 ежемесячно или $4,50 при годовой оплате [15].

ClickUp

primary evidence Для широкого набора бизнес-процессов: nested subtasks [19], custom task types [24], Markdown API [20], GitHub [21], export [22]. Компромисс — объём настроек.

Jira: выбирать, если это уже корпоративный стандарт. Для нового BMAD-процесса иерархия менее удобна, API использует ADF вместо Markdown, а расширенные возможности зависят от тарифа [16] [17] [18].
