# JEV vs Laya для определения частотности английских слов

## Резюме решения

**Короткий ответ: Laya нельзя просто подставить вместо JEV и продолжить показывать `frequency_per_million`. Более того, публичные контракты не подтверждают, что сам JEV умеет возвращать такую метрику.** Обе системы — модели типизированных решений: они выбирают категорию, оценивают позицию на заданной порядковой шкале или возвращают вероятность ответа «да». Опубликованные контракты не предоставляют корпусный подсчёт или fpm [1][2][4].

Laya можно использовать вместо JEV в двух более узких смыслах:

1. **Как локальный движок, совместимый по общей форме API**, для распространённых вызовов `choice` / `score` / `noul`. Официальный сервер Laya реализует Jev-подобный `/v1/systemone`, но лимиты вариантов, правила валидации и семантика confidence отличаются. Модель открыта под Apache-2.0 и может работать локально [4][5][10].
2. **Как обучаемую основу для оценки частотного диапазона**, если собрать корпусные метки, дообучить модель или отдельный head, откалибровать ответы и пройти закрытый тест. Авторы Laya прямо предупреждают, что базовые checkpoints слабы zero-shot на новых задачах и ценность появляется после специализации [4].

Для Lexickon рациональнее сделать **корпусную частоту источником истины**, а Laya оставить дополнительным компонентом: классификация контекста, нормализация запроса, оценка диапазона для OOV/неологизмов или резервный путь с явной маркировкой `estimated`. По инженерной оценке, это проще и объяснимее, чем обучать 421M-модель воспроизводить таблицу частот; стоимость следует проверить отдельно.

Главное следствие для текущего PRD: набросок `POST /v1/frequency → frequency_per_million` не соответствует опубликованному API JEV. Публичный JEV endpoint — `/v1/systemone`; `Score` возвращает математическое ожидание **индексов до десяти заданных уровней**, а не произвольную физическую величину [2][3]. Контракт частотности в PRD следует пересмотреть до архитектуры и stories.

## Что в действительности делают JEV и Laya

| Свойство | JEV | Laya |
|---|---|---|
| Основная функция | Hosted System One decision model | Локальная/open-weight System One decision model |
| Выходы | `choice`, ordinal `score`, `noul` | `choice`, ordinal `score`, `noul` |
| Нативный corpus count / fpm / Zipf | Не документирован | Не документирован |
| Интерфейс | `POST /v1/systemone` | Self-hosted `/v1/systemone`, совместимый по общей форме запроса и ответа |
| Модель | Закрытая, hosted | English checkpoint: ModernBERT-large + decision head, 421M |
| Адаптация под свои метки | Клиент задаёт критерии; customer fine-tuning публично не документирован | Fine-tuning и отдельный fitted head возможны |
| Лицензия/развёртывание | Проприетарный API | Apache-2.0, локально CPU/CUDA/MPS |
| Текущая эксплуатация | $0.042 за 1M input tokens; 1200 req/min; pin version рекомендуется | Бесплатный inference, но свои hardware/ops; benchmark нужен на целевом устройстве |

JEV `Score` — это не числовая регрессия. Пользователь задаёт 2–10 словесно описанных уровней; API возвращает распределение по ним и взвешенное среднее их индексов. Документация отдельно предупреждает, что голые числа в описаниях уровней модели не помогают [2]. Поэтому шкала вроде `0, 1, 10, 100, 1000 fpm` даст лишь субъективное распределение по текстовым категориям. Его нельзя честно назвать наблюдаемой частотой.

Laya устроена аналогично. Её выходной слой сравнивает заданные варианты с помощью маркеров. Опубликованный контракт не предоставляет вероятность токена, поиск по корпусу, регрессию по шкале Zipf или подсчёт н-грамм [4][5].

## Что означает «частотность»

`frequency_per_million` — это свойство конкретного корпуса:

```text
fpm = observed_occurrences / corpus_token_count × 1,000,000
```

SUBTLEX-US, например, считает эту величину по корпусу американских субтитров объёмом 51 млн слов и отдельно хранит contextual diversity — долю фильмов, в которых встречается слово [7]. Исследования показывают, что жанрово-стилевой состав корпуса влияет на полезность метрики, а contextual diversity иногда лучше сырого количества предсказывает узнавание слова [7][8].

Zipf-шкала удобнее для UI и моделирования:

```text
Zipf = log10(occurrences per billion) = log10(fpm) + 3
```

Следовательно, `1 fpm = Zipf 3`, `10 fpm = Zipf 4`, `100 fpm = Zipf 5` [7][9]. На ней ошибка `1.0` означает примерно десятикратную ошибку частоты.

### Слова и фразы — разные задачи

Для одиночных слов практичным baseline является `wordfreq`: он объединяет несколько источников и возвращает Zipf frequency. Однако для многословного запроса он применяет эвристику суммы обратных частот отдельных токенов, а не наблюдаемое количество фразы [9]. Для `transformer architecture`, phrasal verbs и idioms нужны реальные n-граммные counts из COCA, другого лицензированного корпуса или собственного датасета.

## Качество и риски Laya

Официальные материалы Laya называют модель «fast base to specialise, not a zero-shot decision engine»: base checkpoint получил около 0.36 на собственном typed-decisions benchmark, fine-tuned checkpoint — 0.766 [4]. `score` описан как самый слабый primitive на одном из опубликованных тестов, а calibration зависит от задачи и должна перепроверяться на своём распределении [4].

В независимом тесте `sysone-bench` на идентичных входных данных JEV 1.13 получил 0,9065, а Laya 0.3.11 — 0,6863 на 1 240 типизированных решениях [6]. У набора есть два ограничения: разметку проверял один человек без второй независимой проверки, а сам тест не измеряет частотность лексики. Это не доказывает превосходство JEV в нашей задаче, но опровергает идею, что совместимость API означает одинаковое качество.

Laya быстра локально: авторы сообщают десятки миллисекунд на прогретом GPU, но сотни миллисекунд на CPU и многосекундную cold load. Кроме того, выбор между bf16 и fp32 может менять вероятности, а иногда и результат `argmax`. Для production нужно закрепить checkpoint revision, версию runtime, dtype и тип устройства [4][5].

## Рекомендация для Lexickon

1. **Не менять JEV на Laya как прямой источник `frequency_per_million`**, потому что у обоих нет подтверждённого контракта такой метрики.
2. **Исправить продуктовый термин и API-контракт**:
   - наблюдаемый count → `frequency_per_million`, обязательно с `corpus_id`, версией и срезом;
   - нейросетевой ответ → `estimated_commonness_band` или `estimated_zipf`, с `model_version`, confidence и признаком `estimated`;
   - `confidence` модели не трактовать как вероятность появления слова.
3. **Для MVP взять локальный versioned lookup** одиночных слов. Чтобы учитывать полезность слова для изучающего язык, стоит хранить не только fpm и Zipf, но и contextual diversity.
4. **Для фраз использовать настоящий n-граммный источник**. Не выдавать multi-token результат `wordfreq` за phrase fpm.
5. Если важны неологизмы и сдвиг распределения данных, провести отдельный пилот Laya как резервного механизма, но не блокировать на нём MVP.

## Минимальный pilot, если всё же проверять Laya

В качестве стартовой инженерной гипотезы собрать закрытый тестовый набор из 1 000–2 000 запросов с отдельными срезами; окончательный размер определить через power/error analysis:

- частые, средние и редкие word forms;
- inflections, capitalization, proper names и spelling variants;
- 2–5-word phrases и idioms;
- technical/academic vocabulary;
- неологизмы, OOV и правдоподобные несуществующие строки.

Эталонные метки должны быть получены из зафиксированного корпуса, а не из JEV. Сравнить corpus lookup, `wordfreq` для одиночных слов, JEV zero-shot, Laya zero-shot и fine-tuned Laya. Для непрерывного результата использовать Zipf MAE/RMSE, Spearman и долю ответов в пределах ±0,5/±1,0 Zipf; для диапазонов — macro-F1, ordinal MAE, ECE/Brier и risk-coverage с отказом от ответа. При изменении checkpoint, prompt, corpus или dtype тест повторяется.

## Сильнейший аргумент против рекомендации

Модель может лучше старого корпуса угадывать новые и доменные выражения. Это правдоподобно, но сейчас не подтверждено ни для JEV, ни для Laya. Без датированного тестового набора современного языка это преимущество остаётся гипотезой. Наиболее дешёвый обратимый ход — корпусный lookup как baseline плюс скрытый теневой прогон моделей, после чего сравнить их с обновлённым срезом веб- и новостных текстов.
