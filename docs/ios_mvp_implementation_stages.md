# Lexickon iOS: поэтапный план разработки MVP

## Назначение документа

Этот документ превращает архитектурный план iOS-клиента в 12 последовательно
выполняемых этапов. Каждый этап должен завершаться проверяемым инкрементом и не
смешиваться с работами следующих этапов.

Базовые технические предпосылки:

- UI — SwiftUI, минимальная версия — iOS 26;
- асинхронность — Swift Concurrency;
- состояние UI — Observation;
- навигация — иерархический Step-Driven Coordinator;
- DI — ручной Composition Root (`AppContainer`);
- сеть — типизированный клиент на `URLSession`;
- токен — Keychain;
- содержимое датасетов — локальные immutable SQLite-паки.

Если один из открытых вопросов в конце документа меняет публичный контракт уже
реализованного компонента, решение фиксируется до начала зависимого этапа.

## Этап 1. Каркас приложения

### Цель

Создать собираемый проект и минимальную структуру, на которую можно безопасно
наращивать функциональность.

### Ожидаемый результат

Приложение запускается на iOS 26 simulator, показывает временный стартовый
экран, а targets приложения, unit-тестов и UI-тестов собираются одной схемой.

### Границы задачи

Входит:

- создание `LexickonApp`, `LexickonTests` и `LexickonUITests`;
- базовые build settings и конфигурации Debug/Release;
- каталоги `App`, `Navigation`, `Domain`, `Data`, `Features`, `Core`,
  `Resources`;
- `Assets.xcassets` и `Localizable.xcstrings`;
- минимальный app entry point и placeholder UI;
- базовые правила логирования без пользовательских секретов.

Не входит:

- DI-граф и реальные сервисы;
- рабочая навигация;
- API, авторизация и хранение токена;
- продуктовые экраны.

### Критерии готовности

- Проект открывается без ручного исправления путей или signing settings.
- Все три targets видны в схеме и собираются.
- Приложение запускается без crash и предупреждений о недостающих ресурсах.
- В feature-коде нет глобальных singleton и преждевременно выбранных сторонних
  архитектурных библиотек.
- Строки placeholder-экрана готовы к локализации.

### Проверка и тесты

- Выполнить clean build Debug для iOS 26 simulator.
- Запустить пустой unit-test target.
- Запустить стартовый UI smoke test: launch и наличие placeholder-экрана.
- Собрать Release-конфигурацию, чтобы выявить расхождения build settings.

## Этап 2. Архитектурная основа и Dependency Injection

### Цель

Зафиксировать границы слоёв, контракты основных зависимостей и единый способ
сборки production- и test-графа.

### Ожидаемый результат

`AppContainer` создаёт зависимости приложения в Composition Root, а feature
типы получают узкие протоколы или use cases через initializer injection.
Domain не зависит от SwiftUI, URLSession, Keychain или SQLite.

### Границы задачи

Входит:

- Domain entities и протоколы `AuthRepository`, `UserRepository`,
  `DatasetRepository`, `FrequencyRepository`;
- скелеты основных use cases;
- `AppContainer` и разделение production/test assembly;
- общая модель типизированных ошибок;
- test doubles для репозиториев, clock/UUID при необходимости;
- правила actor isolation и `Sendable` для типов на границах concurrency.

Не входит:

- реальные реализации сети, Keychain и SQLite;
- состояние конкретных экранов;
- переходы Coordinator;
- бизнес-логика, зависящая от ещё не подтверждённого API/SQL-контракта.

### Критерии готовности

- Production-граф собирается только в Composition Root.
- `AppContainer` не передаётся вниз как service locator.
- Feature/ViewModel можно создать с test doubles без сети и файловой системы.
- Domain target/namespace не импортирует инфраструктурные фреймворки.
- Ошибки имеют стабильное разделение на transport, authorization, dataset,
  local storage и presentation-friendly состояния.

### Проверка и тесты

- Unit-тестом собрать минимальный test container.
- Проверить подмену каждого repository test double.
- Добавить архитектурную проверку импортов или code review checklist для
  направления `Features -> Domain <- Data`.
- Запустить Thread Sanitizer на минимальном тесте shared session state, если
  actor состояния уже создан.

## Этап 3. Навигация

### Цель

Реализовать корневую иерархическую навигацию, не связывая её с сетевыми или
бизнес-операциями.

### Ожидаемый результат

`AppCoordinator` переключает placeholder flows Authentication, Dataset Setup и
Main через типизированные Step и результаты дочерних Coordinator. Завершённый
root flow нельзя открыть системным жестом «назад».

### Границы задачи

Входит:

- `CoordinatorStep` и базовый контракт Coordinator;
- `AppStep`, `AuthStep`, `DatasetSetupStep`, `MainStep`;
- `AppCoordinator`, дочерние coordinator и типизированные child results;
- хранение `NavigationStack` path, sheet/full-screen state и selected tab;
- создание, удержание и освобождение дочерних coordinator;
- placeholder-маршруты logout/session-expired.

Не входит:

- реальные формы авторизации;
- session bootstrap;
- загрузка или установка датасета;
- deep links и полное state restoration, пока это отдельно не согласовано.

### Критерии готовности

- Каждый coordinator принимает только собственный Step.
- Дочерний coordinator не знает Step родителя.
- Root replacement очищает историю завершённого flow.
- Coordinator остаётся на `@MainActor` и не выполняет сетевую/SQLite-работу.
- Повторный Step или быстрые последовательные события не создают дубликаты
  экранов и дочерних coordinator.

### Проверка и тесты

- Unit-тесты таблицы переходов каждого coordinator.
- Unit-тесты преобразования child result в Step родителя.
- Тест создания и освобождения дочернего coordinator.
- UI-тест placeholder-сценария Authentication -> Dataset Setup -> Main ->
  Logout и проверка отсутствия возврата назад.

## Этап 4. Сеть и сессия

### Цель

Создать безопасную инфраструктуру API и локальной сессии до реализации
продуктовых запросов.

### Ожидаемый результат

Типизированный API client кодирует запросы, декодирует ответы, нормализует
ошибки, централизованно добавляет Bearer token и восстанавливает сохранённую
сессию из Keychain.

### Границы задачи

Входит:

- `APIRequest`/endpoint abstraction и typed DTO;
- `URLSession` transport с поддержкой cancellation;
- единое декодирование успешных ответов и API errors;
- Keychain-backed `TokenStore`;
- actor для session state;
- централизованная авторизация запросов;
- session bootstrap: отсутствует, потенциально валидна, недействительна;
- redaction пароля, access token и signed URL в логах.

Не входит:

- UI логина/регистрации;
- окончательная refresh-логика до подтверждения backend-контракта;
- каталог и скачивание датасетов;
- произвольный retry небезопасных запросов.

### Критерии готовности

- Авторизованный запрос получает актуальный Bearer token централизованно.
- Пароль и токены не сохраняются вне Keychain и не попадают в логи.
- `401` преобразуется в однозначное событие сессии без циклического retry.
- Cancellation доходит от task до `URLSession`.
- DTO не выходят в Presentation и преобразуются в Domain-модели.
- Неопределённая refresh-стратегия изолирована за контрактом, чтобы её можно
  было добавить без переписывания feature-кода.

### Проверка и тесты

- Unit-тесты URL construction, headers, body encoding и response decoding.
- Тесты mapping для `2xx`, `400`, `401`, `403`, `404`, `5xx`, timeout и
  malformed response через `URLProtocol` stub.
- Тесты сохранения, чтения и удаления токена в изолированном Keychain service.
- Тест session bootstrap при отсутствии, наличии и повреждении токена.
- Тест redaction: секреты отсутствуют в сформированных log messages.

## Этап 5. Авторизация

### Цель

Дать пользователю законченный сценарий регистрации, входа, восстановления
сессии и выхода.

### Ожидаемый результат

Пользователь регистрируется, входит по email/паролю, попадает в следующий root
flow, повторно запускает приложение с восстановленной сессией и может выйти с
полной очисткой пользовательского состояния.

### Границы задачи

Входит:

- экраны Login и Registration;
- валидация полей и состояния idle/loading/success/error;
- реализации `AuthRepository` и auth use cases;
- сохранение токена только после успешного логина;
- переход регистрации обратно к логину при текущем backend-контракте;
- обработка invalid/expired session;
- logout и очистка session-scoped состояния.

Не входит:

- password recovery;
- Sign in with Apple и социальная авторизация;
- профиль и настройки;
- выбор и установка датасета.

### Критерии готовности

- Повторная отправка формы блокируется во время запроса.
- Клиентские validation errors отличаются от API/transport errors.
- Ошибка логина не повреждает ранее согласованное состояние сессии.
- После успеха Authentication flow освобождается и заменяется следующим root.
- Logout удаляет токен, очищает session-scoped кэш и возвращает Authentication.
- После cold launch валидная сессия не требует повторного ввода пароля.

### Проверка и тесты

- Unit-тесты validation и переходов состояния Auth ViewModel.
- Integration-тесты регистрации, логина и авторизованного запроса к профилю.
- Тесты `401` во время bootstrap и во время активной сессии.
- UI-тесты success/error сценариев Login и Registration.
- UI-тест Login -> relaunch -> восстановленная сессия -> Logout.

## Этап 6. Каталог датасетов

### Цель

Получать доступные датасеты и принимать воспроизводимое решение о новой
установке, обновлении или сохранении локальной версии.

### Ожидаемый результат

Приложение показывает каталог/manifest, знает метаданные установленных паков и
формирует sync actions без скачивания содержимого на этом этапе.

### Границы задачи

Входит:

- DTO и Domain-модели manifest, dataset version и sync action;
- реализация catalog/sync части `DatasetRepository`;
- локальный реестр установленных датасетов: `dataset_key`, data version,
  schema version, checksum, дата установки и update state;
- сопоставление языка, домена, размера и статуса доступности;
- состояния revoked, deprecated, forbidden и incompatible;
- получение временной signed download URL как отдельная операция.

Не входит:

- скачивание, checksum, распаковка и атомарная установка;
- UI первичной настройки;
- чтение frequency records;
- окончательный выбор обязательного датасета без продуктового решения.

### Критерии готовности

- Одинаковая пара manifest + local registry всегда даёт одинаковый sync plan.
- Более старая, отозванная или несовместимая версия не выбирается как update.
- Signed URL не сохраняется как постоянная метаинформация.
- Пустой каталог и частично недоступные элементы имеют явные Domain-состояния.
- Повреждённая запись локального реестра не объявляет pack установленным.

### Проверка и тесты

- Unit-тесты DTO-to-Domain mapping.
- Табличные тесты sync decision: install, keep, update, revoke, incompatible,
  forbidden.
- Integration-тест manifest -> sync actions -> signed URL на stub backend.
- Тест миграции/повреждения локального реестра.
- Тесты сортировки и фильтрации каталога по языку/домену.

## Этап 7. Безопасная установка датасета

### Цель

Реализовать устойчивую установку SQLite-пака без риска заменить рабочую версию
повреждённым или несовместимым файлом.

### Ожидаемый результат

Пак скачивается во временную область, проверяется, распаковывается в staging,
валидируется и атомарно становится активным. При любой ошибке прежний pack
остаётся рабочим.

### Границы задачи

Входит:

- download в temporary location с прогрессом и cancellation;
- политика `sync_over_cellular` для автоматической загрузки;
- SHA-256 verification;
- безопасная распаковка без path traversal и выхода за staging directory;
- проверка свободного места и ожидаемого размера;
- SQLite integrity/schema validation;
- атомарное переключение версии и обновление local registry;
- cleanup temporary/staging файлов и retry;
- actor isolation установщика.

Не входит:

- полноценная фоновая/возобновляемая загрузка до решения открытого вопроса;
- UI первичной настройки;
- реализация продуктового `offline_mode`;
- frequency query, кроме минимальной schema probe для совместимости.

### Критерии готовности

- Checksum вычисляется до распаковки/активации и сравнивается с manifest.
- Ни checksum mismatch, ни ошибка распаковки/схемы не заменяет рабочий pack.
- Переключение активной версии и registry не оставляет промежуточного состояния.
- Отмена операции завершает активную работу и очищает временные артефакты.
- Одновременные установки одного dataset serialised или безопасно deduplicated.
- Логи не содержат signed URL.

### Проверка и тесты

- Unit-тесты checksum match/mismatch и правил cellular download.
- Integration-тест установки fixture pack и последующего открытия SQLite.
- Fault-injection тесты: обрыв download, мало места, повреждённый архив,
  zip traversal, неверная schema version, сбой перед atomic replace.
- Тест, что рабочая версия сохраняется после каждого вида ошибки.
- Тест cancellation и очистки temporary/staging.
- Тест конкурентного запуска двух установок одного dataset.

## Этап 8. Первичная настройка

### Цель

Провести нового или не полностью настроенного пользователя от выбора данных до
готового локального датасета.

### Ожидаемый результат

Dataset Setup flow позволяет выбрать язык и домены, увидеть размер, установить
обязательный pack, повторить операцию после ошибки и перейти в Main только после
успешной проверки установки.

### Границы задачи

Входит:

- выбор предпочитаемого языка и доменов;
- отображение размера и ограничений cellular;
- состояния preparing/downloading/verifying/installing/ready/error;
- прогресс, cancellation в безопасных точках и retry;
- сохранение согласованных настроек через существующий контракт;
- проверка обязательного dataset перед `datasetSetupCompleted`;
- повторный вход в setup при отсутствующем/повреждённом обязательном pack.

Не входит:

- управление всеми обновлениями из Profile;
- локальный frequency query;
- фоновая установка после завершения приложения;
- необязательные onboarding-экраны и обучение.

### Критерии готовности

- Main недоступен, пока обязательный pack не установлен и не проверен.
- UI однозначно различает download, checksum, schema, disk-space и network
  ошибки и предлагает подходящее действие.
- Повторный запуск продолжает с корректного устойчивого состояния, а не с
  временного шага установки.
- Изменение выбора пересчитывает размер и требуемый набор паков.
- Завершённый Setup flow удаляется из back stack.

### Проверка и тесты

- Unit-тесты состояния Dataset Setup ViewModel.
- Unit-тест gate-функции «можно ли открыть Main».
- UI-тест happy path выбора, загрузки и перехода в Main.
- UI-тесты ошибки сети/checksum/места и успешного retry.
- Relaunch-тесты до установки, во время прерванной установки и после ready.
- Тест поведения при cellular и выключенном `sync_over_cellular`.

## Этап 9. Локальный поиск

### Цель

Создать изолированный слой чтения установленного SQLite-пака и Domain API для
поиска частотности.

### Ожидаемый результат

`FrequencyRepository` принимает нормализованный запрос и контекст датасета,
выполняет локальный SQL вне MainActor и возвращает типизированный результат или
понятное состояние ошибки.

### Границы задачи

Входит:

- SQLite connection/query executor с безопасной concurrency model;
- выбор активного dataset по языку/домену;
- параметризованный SQL и нормализация пользовательского запроса;
- результат found/not found/dataset unavailable/incompatible/corrupted;
- версия и источник датасета в результате;
- lifecycle соединения при атомарной смене активного pack.

Не входит:

- экран ввода и отображения результата;
- история, избранное, сравнение и аналитика;
- удалённый fallback поиска к API;
- фиксация окончательного SQL/нормализации без подтверждённого контракта.

### Критерии готовности

- UI/ViewModel не импортируют SQLite API.
- Пользовательский ввод передаётся только как bound parameter.
- Запрос не выполняется на MainActor.
- Чтение либо заканчивается на старой согласованной версии, либо начинается на
  новой; оно не видит наполовину заменённый файл.
- Не найденное значение не смешивается с нулевой частотностью.
- Несовместимая/повреждённая база приводит к управляемому Domain error.

### Проверка и тесты

- Fixture-пак покрывает found, not found, регистр, пробелы, Unicode и фразу.
- Тест exact SQL contract и query plan после его утверждения.
- Тест защиты от SQL injection через параметризованный ввод.
- Performance-тест типового и предельного запроса на целевом устройстве.
- Concurrency-тест параллельных чтений и смены версии.
- Тесты отсутствующего, закрытого и повреждённого SQLite-файла.

## Этап 10. Экран частотности

### Цель

Дать пользователю основной MVP-сценарий: быстрый локальный поиск слова или
фразы и понятное отображение результата.

### Ожидаемый результат

Вкладка Frequency объединяет поле ввода и результат, показывает значение,
единицу/нормализацию, язык, домен и версию датасета и помогает исправить
отсутствующий или несовместимый pack.

### Границы задачи

Входит:

- Frequency View и ViewModel;
- состояния initial/empty/loading/result/not found/error;
- запуск с клавиатуры и явной кнопкой;
- защита от показа устаревшего результата при быстрых повторных запросах;
- доступность и локализация;
- переход к управлению датасетами при dataset unavailable/incompatible.

Не входит:

- история запросов;
- избранное и сравнение;
- графики и расширенная аналитика;
- поиск содержимого через backend.

### Критерии готовности

- Пустой/пробельный ввод не запускает SQLite query.
- Новый запрос отменяет или логически инвалидирует предыдущий.
- Result явно сообщает метрику, единицу и dataset context.
- Not found визуально отличается от технической ошибки и значения `0`.
- Локальный поиск работает без сети при установленном совместимом pack.
- Dynamic Type, VoiceOver labels и управление клавиатурой не блокируют
  основной сценарий.

### Проверка и тесты

- Unit-тесты всех переходов Frequency ViewModel.
- Тест race: медленный первый ответ не перезаписывает быстрый второй.
- Snapshot/visual checks для ключевых состояний и крупных Dynamic Type.
- UI-тест happy path, not found и перехода к Dataset Setup/management.
- UI-тест запуска в airplane/offline environment с установленным pack.
- Performance measurement от submit до отображения локального результата.

## Этап 11. Профиль и настройки

### Цель

Предоставить пользователю просмотр профиля, управление настройками и
установленными датасетами, а также безопасный logout.

### Ожидаемый результат

Вкладка Profile показывает email, языки/домены, `offline_mode`,
`sync_over_cellular`, версии паков и обновления; подтверждённые изменения
синхронизируются с `PATCH /me/settings`.

### Границы задачи

Входит:

- загрузка и отображение профиля;
- изменение поддержанных сервером настроек;
- согласованная стратегия update: pessimistic либо optimistic с rollback;
- список установленных датасетов и доступных обновлений;
- ручная синхронизация с переиспользованием безопасного installer;
- logout через единый auth/session use case;
- состояния загрузки, сохранения, ошибки и retry.

Не входит:

- изменение email/пароля, если отсутствует API-контракт;
- удаление аккаунта;
- незафиксированная продуктовая семантика `offline_mode`;
- обязательная фоновая синхронизация.

### Критерии готовности

- UI не показывает настройку сохранённой, если сервер её отклонил.
- При optimistic update выполняется rollback и сообщается ошибка.
- `sync_over_cellular` влияет на следующие автоматические загрузки.
- Ручной update не может повредить текущий установленный pack.
- Logout очищает токен и session-scoped данные и заменяет root на Auth.
- Недоступный backend не мешает просмотреть локальные версии паков.

### Проверка и тесты

- Unit-тесты mapping профиля и переходов Profile ViewModel.
- Integration-тест GET profile и PATCH settings, включая server rejection.
- Тест optimistic rollback либо pessimistic commit выбранной стратегии.
- UI-тест Profile -> изменение настройки -> relaunch -> сохранённое значение.
- UI-тест ручного обновления и отображения новой версии.
- UI-тест Logout и невозможности вернуться жестом в Main.

## Этап 12. Финальная проверка MVP

### Цель

Подтвердить, что собранный продукт выполняет MVP-сценарии целиком, устойчив к
основным отказам и готов к передаче на релизную приёмку.

### Ожидаемый результат

Есть воспроизводимый release candidate, отчёт о тестировании и зафиксированные
остаточные риски. Все критерии MVP либо доказаны, либо явно вынесены из релиза
с продуктовым решением.

### Границы задачи

Входит:

- интеграция с целевым FastAPI environment;
- полный unit/integration/UI regression run;
- проверка fresh install, update и relaunch;
- тесты offline/cellular/low-disk/corrupt-pack/session-expired;
- security/privacy review Keychain, логов и signed URLs;
- accessibility, локализация и базовая производительность;
- Release build, smoke на simulator и поддерживаемом физическом устройстве;
- фиксация известных ограничений и release checklist.

Не входит:

- новые продуктовые функции;
- рефакторинг без влияния на критерии релиза;
- история поиска, социальная авторизация и расширенная аналитика;
- замена согласованных контрактов непосредственно перед релизом.

### Критерии готовности

- Проходит сценарий Register -> Login -> Dataset Setup -> Frequency Search ->
  Profile -> Logout.
- Валидная сессия и установленный pack корректно восстанавливаются после cold
  launch.
- Локальный поиск работает без сети и не отправляет содержимое запроса к API.
- Любая неуспешная установка сохраняет предыдущий рабочий pack.
- Нет утечек пароля, токена и signed URL в логах/analytics/crash context.
- Root flows не остаются в back stack.
- Все blocking/critical дефекты закрыты, остальные имеют владельца и решение.
- Release build устанавливается, запускается и проходит smoke на iOS 26.

### Проверка и тесты

- Запустить весь набор unit-тестов с включённым code coverage и разобрать
  непокрытые критические ветви.
- Запустить integration suite против согласованного тестового backend и fixture
  packs.
- Запустить UI smoke и failure-path suite минимум дважды на чистой установке.
- Провести Network Link Conditioner/airplane-mode и low-storage проверки.
- Выполнить Instruments-проверки hangs, memory и file/SQLite activity в
  сценариях установки и поиска.
- Провести ручной accessibility pass с VoiceOver и крупным Dynamic Type.
- Проверить архивирование Release и сформировать подписанный checklist
  приёмки.

### Основной порядок

```text
1 Каркас
└── 2 Архитектура/DI
    ├── 3 Навигация
    └── 4 Сеть и сессия
        └── 5 Авторизация
            └── 6 Каталог датасетов
                └── 7 Безопасная установка
                    └── 8 Первичная настройка
                        └── 9 Локальный поиск
                            └── 10 Экран частотности
                                └── 11 Профиль/настройки
                                    └── 12 Финальная проверка
```

### Точные входные зависимости

| Этап | Требует | Причина |
| --- | --- | --- |
| 1 | — | Создаёт проект и targets. |
| 2 | 1 | Контракты и DI должны быть частью собираемого проекта. |
| 3 | 2 | Coordinator создаётся через Composition Root и использует общие ошибки/состояния. |
| 4 | 2 | Реализации сети и session store подключаются к Domain-контрактам. |
| 5 | 3, 4 | Auth объединяет UI-навигацию, API и сессию. |
| 6 | 4, 5 | Каталог требует авторизованного API и session lifecycle. |
| 7 | 6 | Installer использует manifest, checksum, schema metadata и signed URL. |
| 8 | 3, 5, 6, 7 | Setup связывает root flow, пользователя, каталог и installer. |
| 9 | 2, 7 | Поиск читает только проверенный и атомарно установленный pack. |

## Открытые вопросы и точки принятия решений

1. **SQL-контракт frequency query.** До завершения этапа 9 зафиксировать имена
   таблиц/колонок, ключ поиска, индексы, правила Unicode/case/whitespace
   normalization, семантику phrase lookup и поддерживаемую schema version.
   Подготовить официальный fixture pack и эталонные запросы.

2. **Метрика частотности.** До UI-контракта этапа 10 определить, что означает
   число: абсолютный count, частота на миллион, percentile или другая метрика;
   зафиксировать единицу, округление, `0` против not found, отображаемый источник
   и возможность сравнения между доменами/версиями.

3. **Обязательный датасет.** До gate-логики этапа 8 определить минимальный набор,
   который открывает Main: один pack предпочитаемого языка, pack конкретного
   домена или иной набор. Зафиксировать поведение, если pack revoked,
   недоступен пользователю или временно отсутствует в manifest.

4. **Token refresh.** До финализации этапов 4–5 подтвердить срок жизни access
   token, наличие refresh token/endpoint, ротацию, защиту от параллельных refresh
   запросов и правило выхода при неуспехе. Если refresh не поддерживается,
   явно принять повторный login после `401`.

5. **`offline_mode`.** До реализации настройки на этапе 11 определить, запрещает
   ли режим все control-plane запросы, только автоматическую синхронизацию или
   разрешает явные действия пользователя; как он взаимодействует с bootstrap,
   устаревшим manifest и локальным поиском.

6. **Фоновая загрузка.** До production-hardening этапа 7 определить, нужны ли
   background `URLSession`, возобновление после termination, pause/resume,
   системные уведомления и ограничения battery/network для больших паков.
   Если это не MVP, документировать foreground-only ограничение.

7. **State restoration.** До финального navigation regression этапа 12 решить,
   восстанавливается ли точный navigation path или только устойчивый root state
   (Auth / Dataset Setup / Main). Отдельно определить поведение незавершённой
   установки и открытого экрана результата после process termination.

## Правило фиксации решений

Каждое принятое решение из списка выше должно получить:

- владельца и дату;
- ссылку на API/schema/product contract;
- отражение в Domain-моделях и критериях зависимого этапа;
- положительный и отрицательный тест-кейс;
- заметку о миграции, если решение меняет уже выпущенные данные или сессию.
